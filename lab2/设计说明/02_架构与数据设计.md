# 架构与数据设计

初稿日期：2026年11月13日；局部修订日期：2026年11月17日。版本：已按HREV-002保留主子订单并补充支付关联，其余设计继续审查。

## 1 架构选择与理由

采用模块化单体：同一后端进程承载M01～M11、定时任务及模拟适配器，使用单个MySQL数据库。界面层负责输入、状态展示和反馈；应用层按用例组织权限及事务；领域层维护状态与不变量；基础设施层实现持久化、加密、模拟渠道及设备缓存。逻辑模块并不要求单独部署。

这一选择降低课程原型的部署和分布式一致性成本。购票、候补、退款、转赠与核销共享票据及占位，使用本地短事务更容易表达原子性。性能目标仍须后续按REQ-033测试，不能由架构图推定已经达标。后端语言及框架暂不绑定，模块接口可以用面向对象语言实现。

M04统一维护票据、凭证和有效占位；M02维护容量配置，变更时读取占位下限；M05调度候补；M06协调退款及取消；M07、M08分别维护转赠和核销历史，通过应用用例使用M04的状态转换。M09处理用户消息，M10查询汇总，M11写不可改删审计。M01对每个受保护操作校验当前身份、归属和字段范围。

## 2 应用接口草案

| 用例接口 | 输入与关键返回 | 权限与前置校验 |
|---|---|---|
| AuthService.login / grantRole | 登录结果、角色及授权范围 | 授权仅管理员；普通和管理员身份不兼任 |
| EventService.submitReview / approve / change | 活动版本、审批结果 | 组织者归属、管理员审批、核心变更暂停新售 |
| QueryService.search / detail / subscribe | 组合结果、价格区间、订阅 | 公开查询，订阅登录；开售提醒不占位 |
| TicketService.createOrder | requestId、同场次1～4个观演项目；订单或明确拒绝 | 登录、时段、售票状态、实名、座位、库存、候补优先 |
| PaymentService.applyResult / expire | 交易号、paidAt、订单号；原处理结果 | 内部模拟结果入口、幂等与当前状态校验 |
| WaitlistService.join / withdraw / promote | 身份、场次、票种、序号、递补结果 | 服务端入队顺序、资格、截止与库存 |
| RefundService.request / applyResult | 子票集合、退款键、结果与进度 | 原购票人、持票归属、锁定、时限、原账户 |
| CancellationService.cancel / startBatch | 范围、原因、例外比例及批次号 | 组织者申请管理员批；例外比例仅管理员且执行前 |
| TransferService.start / accept / withdraw / return | 票据、接收人、申请版本；新持票及凭证 | 实名唯一、时间、次数、活动及票据有效性 |
| CheckInService.verify / sync / correct | 凭证、设备事件、申请与审批；核销或异常结果 | 当前场次授权、时间、锁定、凭证、纠错审批 |
| OperationsService.export / statistics | 筛选条件、授权范围；名单及汇总 | 脱敏与导出权限；检票人员不能批量导出 |
| AuditService.query | 人、时间、类型、对象；审计记录 | 仅管理员查询，不提供编辑删除接口 |

这些是设计接口而非已经存在的HTTP服务。请求返回需区别成功、预期业务拒绝、处理中与技术错误；处理中不改写支付/转赠期限。真实路径、错误码及密码策略在实现前细化。

## 3 数据存储草案

标识使用UUID；货币采用精确十进制类型和币种，禁止二进制浮点；具体精度及舍入规则尚待确认。时间在后端统一处理并按场次业务时区展示。所有表包含必要的创建时间和版本字段；历史记录与当前有效关联分开。

| 数据集合 | 关键字段和关联 | 主要约束 |
|---|---|---|
| users、role_grants | 用户、账号类别、角色、活动/场次范围 | 账号唯一；校验身份兼任限制 |
| identities、user_spectators | 实名键、密文身份/手机号、账号与观演人关联 | 同一实名跨账号使用同一规范化身份键；允许代购 |
| events、sessions、ticket_types、session_seats | 所属活动、起止、状态、容量、区域、价格及规则版本 | 外键关联；区域合计上限；历史票种不物理删除 |
| orders、tickets | 请求号、原购票人、子票身份、当前持票人、场次票种、成交及规则快照、状态、锁定 | 请求号全局唯一且绑定调用者；同请求不同载荷不能新增订单；同一订单只含一个场次 |
| active_claims | ticketId、sessionId、identityKey、可空seatId | 唯一(sessionId,identityKey)；非空seatId在场次内唯一；ticketId唯一 |
| credentials | ticketId、不可预测凭证摘要、版本、撤销时间 | 凭证摘要唯一；每票最多一条当前有效凭证；旧凭证永久失效 |
| wait_entries | 观演人、场次、票种、持久queueSeq、处理状态、递补子票 | 唯一队列序号；同身份/场次/票种最多一条有效排队，历史可保留 |
| payments、refunds、refund_batches | 支付所属主订单orderId、原支付账户、唯一支付流水、退款键、金额、冻结比例与原因 | payments.orderId为指向orders的非空外键；支付流水唯一；同笔退款键幂等；批次启动后比例不变 |
| transfers | 子票、发起/接收方、较早期限、结果、是否原路返还 | 同票最多一个待接收申请；向外成功次数最多一次 |
| checkins、corrections、offline_events | ticketId、发生时间、设备事件号、同步及审批状态 | 设备事件号唯一；每票有效核销不重复；原始核销和更正均保留 |
| reminder_subscriptions、notifications、notification_events | 接收人、业务对象、节点、待通知内容 | 事件绑定已提交业务；不得把通知送达当作期限起算依据 |
| audit_logs | 角色、对象、IP、动作、时间、前后值、结果、原因 | 应用无编辑删除入口，查询仅管理员；不记录完整敏感信息 |

根据HREV-002保留主订单组合1～4张子票的结构。每条Payment通过非空orderId只归属一个主订单；主订单可以没有支付流水，或保留多条历史流水，不以orderId唯一限制历史记录。多条历史流水不代表允许重复出票：处理结果时仍检查订单当前状态和支付流水唯一性，同一结果只应用一次。退款关联原支付流水和子票，据此可从子票追溯主订单、支付及原账户；具体失败/取消支付后的订单策略仍保留待确认。

加密保存身份证号和手机号；唯一性校验使用服务端秘密密钥生成的规范化身份HMAC键，避免随机密文无法比对，也避免把明文证件写入唯一索引。密钥与数据库分离，日志禁记密钥。具体算法、密钥管理与轮换属于实现安全设计，需进一步审查。凭证为不可预测令牌，库中保留摘要；界面示例不是真实凭证。

## 4 一致性与并发

为课程原型选择较易核对的场次行锁：所有影响该场次售票、占位、递补、退款、转赠与核销资格的事务先锁场次，再按稳定顺序锁票种、订单、票据；跨票种整单按ID排序。此方案牺牲部分并发度以换取明确的一致性边界，若压测不达标再依据实测调整，不能提前声称达标。

1. **整单下单**：先按调用者和请求号识别重试，锁场次并重新校验时段及当前状态，验证全部子票、候补优先和唯一占位；同事务写订单、快照、占位、审计及待通知事件。任一项失败全部回滚；免费票已报名，收费票待付。
2. **支付与超时**：模拟支付调用不持有事务锁。结果应用另开事务，结合实际付款时间、当前订单状态和流水唯一性处理。超时任务重复无效；已取消并释放后收到成功结果只记录异常退款，不恢复原票。恰好15分钟的判定细节保留待确认。
3. **释放与递补**：免费取消、普通退款成功、待付超时及容量增加产生释放时，在同一协调事务内优先处理同场同票种有效候补，直接购买也检查该优先规则，避免释放到递补之间被新请求抢占。
4. **普通退款**：申请先转退票中并保留占位；模拟退款返回后新事务应用唯一结果。成功释放，失败且场次正常恢复已报名；若期间取消，退款处理不得恢复资格。
5. **转赠与核销**：统一锁场次及票据，接收前后重新检查实名、次数和截止；持票人、身份占位、历史及新旧凭证一起变更。核销检查最新凭证及转赠锁；只允许一个当前有效凭证。
6. **取消与退款批次**：先提交场次取消标志，使所有资格入口立即拒绝，再分批幂等更新票据、待付、候补和转赠，保留历史。管理员设置已检票例外比例后启动批次冻结；每张子票独立退款键，失败重试不改比例、不累计重复支付。待付关闭释放一次，场次可售显示始终为0。
7. **审计与通知**：关键业务、审计和待通知事件同事务提交，审计失败则回滚。提交后由M09处理通知事件；重试次数、合并及接收对象等未定政策保留为配置/策略待澄清，不能由本稿填成需求事实。
8. **离线同步**：客户端保存设备事件号及发生时间；联网后验证、去重并保存事实，正常迟到可更正缺席。重复、失效凭证或取消场次进入异常复核，不撤销已发生物理入场，也不恢复场次取消资格。

## 5 质量需求的设计落实

- REQ-033：列表/详情用授权后的组合查询和索引，分页尺寸待设计确认；下单和检票使用短事务；依照原环境、数据量、QPS及三轮指标计划验收，含失败样本和真实成功路径。
- REQ-034/035：应用用例鉴权、归属过滤、最少字段返回、数据库敏感字段加密、导出及日志脱敏；生产HTTPS，本地localhost例外记录。离线无法实时撤权的限制显式展示。
- REQ-036：持久化占位、请求/流水/设备事件幂等，重启扫描未终结任务，模拟三类故障验证30秒恢复。年度99.9%仅长期目标。
- REQ-037/038：购票四步、创建分步、必填提示及服务端3秒内业务反馈。原型演示不能替代用户测试或接口性能验收。
- REQ-039：状态转换只经受控方法；当前资格、退款进度、转赠锁和历史核销分别建模。

## 6 设计前提与剩余工作

本方案为AI提出的可实现设计，尚无真实后端、支付、实名认证或性能结果。原型用测试身份表示平台实名状态，不声称连接真实身份认证渠道。原需求已列明的待澄清项继续见01文档第6节；采用策略接口并在相应页面说明业务规则尚待细化，不擅自增加通知重试次数、导出格式、候补选座算法或舍入政策。

后续人工审查尤其需要检查：场次锁对目标性能的影响、取消批次与资格实时失效、身份键与凭证管理、自动任务恢复、离线设备策略以及所有未定边界。
